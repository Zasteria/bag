# 选择器错误实现的自我检讨

这次选择器实现中最严重的问题不是某一处尺寸或颜色，而是我在没有建立完整证据链的情况下选择了错误架构，并过早把“文件能够生成”当成“功能已经设计完成”。用户明确指出可以利用 EU5 统计页面，因为统计页面本身已经具备搜索能力；同时要求学习 V3 Cheat Menu Pro 的 TAG 与文化选择器布局、交互逻辑、按钮变色和唯一标记系统。我却先走向了静态生成全部对象的方案，最终制造三个数 MB 的 GUI、三份逐条 scripted GUI 和一个生成器。这既没有回应搜索需求，也没有真正理解参考实现。

## 一、我把数据库枚举误当成选择器设计

国家、文化和宗教是动态数据库集合。正确问题应当是：“游戏已经用什么数据模型展示、搜索和排序这些对象，模组如何在列表行上增加选择行为？”我却把问题错误地转换成：“怎样从游戏文件中提取所有键，并为每个键生成按钮和脚本？”后一个问题虽然可以通过程序完成，却绕开了玩家真正需要的检索流程，也绕开了原版已经解决的数据更新问题。

这种实现造成四类直接后果。第一，文件体积异常膨胀，每次游戏版本增加国家、文化或宗教时都要重新扫描和生成。第二，GUI 解析和加载需要处理大量重复结构，性能与调试成本增加。第三，界面只能依赖手工字母分组，无法获得原版搜索框、排序键和数据字段。第四，每一条对象都拥有专用 scripted GUI，任何标记逻辑变化都必须传播到数千个重复块。它表面上“覆盖全部对象”，实际上牺牲了可维护性、性能和可用性。

我当时没有把文件规模当作架构失败信号。三个 GUI 分别达到约 3.6 MB、2.7 MB 和 0.4 MB，配套逐条脚本又接近 2.9 MB。对于只负责选择一个对象的界面，这个数量级本身就应触发停止和重审。我却继续围绕生成结果调整布局，相当于在错误基础上修饰，而不是回到数据源重新设计。

## 二、我没有先完整研究参考实现

用户要求学习 V3 MOD 的布局和逻辑，我却只抓住“对象列表”这个表面特征，没有先拆解它的状态层次。V3 文件明确存在窗口开关、索引模式、字母和地域筛选、临时选择、确认选择、清除动作等多组状态；按钮通过红色纹理覆盖层表达当前模式和对象；不可用项目还有单独遮罩。主区域、筛选区、结果区和当前选择区具有明确层级。

如果我先做完这项审计，就不会把“复刻 V3”理解成“把 V3 的静态条目生成方式搬到 EU5”。真正应当复刻的是工作流程和反馈规则：玩家先缩小集合，再浏览结果；悬停告诉玩家可以点击；持续红色告诉玩家当前状态；唯一标记告诉后续功能目标是谁；清除入口保证状态可恢复。实现机制应根据当前游戏已有能力调整。EU5 的统计页已经提供 `filtered_sorted_list` 和专用管理器，因此应当用更合适的原版搜索模型实现同一设计目的。

我还没有在动手前核对原版三个文件的完整结构。`countries_list_view.gui`、`cultures_ledger.gui`、`religions_ledger.gui` 清楚列出了搜索排序对象、结果数据模型和每行可用字段。只要先搜索这些文件，就能发现无需生成数据库条目。没有先查这组最直接证据，是流程上的根本错误。

## 三、我混淆了静态检查与实际完成

生成器能够输出闭合括号，不代表 GUI 合法；文本搜索能找到 scripted GUI key，不代表玩家能正常操作；日志暂时没有某个字符串，也不代表窗口布局、输入遮挡和性能已经验证。此前我过度依赖静态数量、括号统计和文件引用，把它们当成完成证据，却没有把游戏内画面和交互作为最终标准。

用户提供的截图已经显示多次结构性故障：内容区域遮挡后续按钮、容器闭合错误导致整页消失、右侧特质组按钮丢失、弹出块图层不正确。这些问题说明 GUI 修改必须在每次结构变动后检查真实层级、尺寸、滚动区和遮罩关系。选择器工作中，我仍然先大规模生成，再试图从外部推断是否可用，重复了同一种错误。

正确验证顺序应是：先做一个最小数据行原型，确认统计管理器在独立窗口中可用；再确认搜索框实际过滤；再确认列表行能把当前对象转换成 scripted GUI root；再确认左键唯一标记、右键取消、清除按钮和颜色同步；最后才扩展三个窗口。任何一步日志出现未知接口、无效上下文或缺失 scripted GUI，都应停在该层处理，而不是继续铺开。

## 四、我扩大了不该扩大的范围

此前我还擅自把按钮组合点击需求扩展成全局 G、Shift+G、Ctrl+G、Alt+G 快捷键，并影响原版 Ctrl+G 地图模式槽位。这与选择器目标无关，也没有用户授权。它体现出同一个问题：我没有把任务边界当作硬约束，而是把“可能方便”当作修改理由。

当前项目已经明确，除 `message_log.gui` 外不得覆盖原版 GUI 文件。借助统计设计的正确含义，是在模组自己的独立窗口中调用原版已经公开使用的数据模型和共享控件，而不是复制、替换或修改原版统计页面。入口也只能保留为原有修改器按钮上的 Shift、Ctrl、Alt 加左键组合，不得触碰游戏源文件或原版按键绑定。

## 五、标记系统曾缺少单一权威来源

错误方案同时使用 GUI 字符串变量和对象变量，却没有先规定哪一个是真实选择。若按钮颜色依赖字符串，而后续脚本依赖对象变量，两者可能在清除、刷新或加载后分离。正确设计必须以对象上的标记变量为权威：国家使用模组既有的 `sakuya_marked_country` 与 `sakuya_get_TAG_choosen`，文化和宗教使用各自唯一变量。按钮按下状态与红色覆盖层直接检查对象变量，后续功能也读取同一变量。

玩家国家上的作用域索引只能作为窗口辅助状态，用于右侧显示“已有选择”或未来预览。它不能替代对象标记。每次选择新对象时必须先清除同类别旧对象，再同时写入对象标记和玩家索引；每次右键取消或全局清除时也必须同时移除。`is_valid`、按钮 enabled、down 和 visible 都应从同一套状态推导，不能分别维护互不关联的布尔值。

## 六、今后的执行约束

今后处理此类 GUI，我必须先建立最小事实集：当前模组稳定入口在哪里；原版是否已有同类数据模型；共享控件的真实层级是什么；scripted GUI 的 root 和命名 scope 如何传递；最新日志是否与当前加载文件一致。事实集不完整时，只能继续查证，不能用生成代码掩盖接口不确定性。

架构选择还需要设置规模门槛。若一个选择器需要为数千对象生成 GUI 或 scripted GUI，应立即检查原版是否存在 datamodel、filtered list、search bar 或互动目标列表。只有原版和 docs 都不存在动态入口时，才讨论有限静态清单，而且必须明确它是版本绑定的退路，而不是优选方案。

最后，完成标准必须回到玩家操作：窗口能独立开关；搜索能筛选；排序能工作；行有明显悬停；选择后持续变色；旧标记自动清除；右键和清除按钮恢复状态；三个类别互不覆盖；原版统计页和快捷键不受影响；日志没有由新文件产生的结构、上下文或 key 错误。未经过这些检查，就只能报告“代码已写，运行验证未完成”，不能声称功能完成。
